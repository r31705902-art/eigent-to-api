# Обновление существующего Railway deployment

## Что уже установлено живыми тестами

На `https://eigent-to-api-production.up.railway.app`:

- health, наличие сессии и каталог моделей — HTTP 200;
- gpt-6-astra: короткий Chat запрос и нативный Responses — HTTP 403;
- ограниченный агентный запрос с активными инструкциями и инструментами на gpt-6-astra — HTTP 403;
- модель eigent не объявляет Responses; это проверено, возвращён 400 без генерации;
- агентный запрос к eigent через её Chat transport — HTTP 403.

**Успешной облачной генерации пока не получено.** В предыдущем релизе терялось тело upstream ошибки; установить причину 403 через него невозможно. Нельзя считать доказанным, что это именно Prompt Guard, а не plan/access/WAF.

## Один обязательный redeploy

1. Замени файлы **в существующем GitHub-репозитории** содержимым папки `eigent-to-api` из архива. Файлы Dockerfile и railway.toml должны по-прежнему быть в корне репозитория, не во вложенной второй папке.
2. Сохрани существующие `API_KEY`, домен и Volume `/data/session`. Сессию и ключ переносить в GitHub не нужно.
3. Задай `API_MODE=eigent-agent` (также значение по умолчанию v0.2). Для сохранения прежней пересылки без агентного цикла — `API_MODE=passthrough`.
4. Commit/push → дождись успешного Railway deployment. Либо Redeploy **после обновления кода**. Redeploy старого commit ничего не исправит.
5. Если Volume отсутствовал и сессия потерялась, снова запусти `login.py --server <HTTPS origin>` на своём ПК.
6. Из папки проекта в Windows CMD:

   ```cmd
   python scripts\smoke.py --base-url https://eigent-to-api-production.up.railway.app --generate
   ```

   API_KEY вводится скрыто. Команда запрашивает статус, каталог, диагностику и делает один агентный тест (может тратить кредиты). Если останется ошибка, выведет её диагностическую запись. Не вставляй ключ в команду или чат.

## Что прислать для продолжения проверки

JSON от `/admin/diagnostics` после одного неуспешного запроса. В нём удаляются известные токены, ключи и URL. **Не** присылай auth.json, `.env` или upstream credentials.

Внутри diagnostic entry:

- `upstream_message` — безопасное извлечение сообщения модели;
- `reason_hint` — только эвристика по явному тексту, не догадка из HTTP-кода;
- `transport_route` — реально использованный протокол;
- `id` — совпадает с `error.diagnostic_id` ответа API.

`/admin/diagnostics` требует Bearer API_KEY, содержит до 20 записей, хранится только в памяти и очищается при рестарте. Не открывай этот маршрут публично без авторизации. В этой single-user реализации API_KEY одновременно является административным ключом.

## Чего этот релиз не обещает

Агентный режим — независимый ограниченный Python runtime на базе активных открытых инструкций Eigent с настоящим исполнением planning/scratch-file tools. Это **не** официальный CAMEL/ListenChatAgent и не полный Workforce. Нет shell, browser, MCP или доступа к credential volumes. Текст инструкций не отключается и не маскируется. Совместимость с политикой облачного прокси не подтверждена: живой агентный тест тоже получил 403.

Если явная upstream причина окажется запретом аккаунта/плана на такой доступ, это не исправляется JSON-полем или system prompt: потребуется разрешённый доступ со стороны Eigent. Архив не содержит обхода проверки и не является доказательством успешного облачного e2e.
